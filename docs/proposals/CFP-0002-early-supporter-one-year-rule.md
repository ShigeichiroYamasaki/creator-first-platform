## 1. 要約

一般サポーター登録の要件を満たしたユーザのうち、次の条件を満たす者を**初期サポーター**とし、その資格を一般／初期の階層を持つ譲渡不能なサポーターSBTで表示する。

> **音楽クリエーターの初期登録時刻から365日未満に、当該音楽クリエーターへのサポーター登録がオンチェーンで確定したユーザであること。**

「1年」はコントラクト上の曖昧さを避けるため、初期ポリシーでは`365日 = 31,536,000秒`と定義する。締切時刻ちょうどは「1年未満」ではないため、一般サポーターとなる。

## 2. 提案理由

初期サポーター資格は、人気や支払額ではなく、活動初期から支援意思を示した事実を可視化するためのコミュニティ資格証明である。音楽クリエーターごとの恣意的な締切や先着人数上限ではなく、公開された共通ルールを適用することで、ユーザが条件を事前に理解でき、第三者が判定を再現できる。

この資格は、配当、収益分配、返済、値上がり益、STOの権利、株主権または自動的なプロトコル議決権を与えない。限定コンテンツやコミュニティ機能へ接続する場合も、別の版管理された特権ポリシー、サブスクリプションおよび権利状態を必要とする。

## 3. 規範的な資格ルール

音楽クリエーター$c$について、次を定義する。

- $R_c$: 正規の音楽クリエーター登録台帳が保持する、音楽クリエーター$c$の変更不能な初期登録時刻
- $S_{c,u}$: ユーザ$u$のサポーター登録が対象チェーンで確定したブロックの時刻
- $W_v$: 適用する初期資格ポリシー版$v$の期間。初期版では`365日`

初期サポーター条件は次のとおりとする。

$$
R_c \le S_{c,u} < R_c + W_v
$$

加えて、`SPEC-ACCOUNT-004`が定めるアカウント、ウォレット連携、支援意思、受領同意、一意性、ファイナリティおよび不正対策を満たさなければならない。これらは一般サポーター登録にも必要な前提であり、初期階層だけの追加条件は上記の時間条件とする。

### 境界の解釈

| サポーター登録確定時刻 | 結果 |
| --- | --- |
| $R_c$より前 | 不正な状態として拒否 |
| $R_c$と同時刻 | 初期サポーター |
| $R_c + 31{,}535{,}999\text{秒}$ | 初期サポーター |
| $R_c + 31{,}536{,}000\text{秒}$ | 一般サポーター |
| $R_c + 31{,}536{,}000\text{秒}$より後 | 一般サポーター |

署名時刻、プレーヤーのクリック時刻、リレイヤー受付時刻またはクライアント時計を資格時刻にしない。支援登録トランザクションがファイナリティ条件を満たした時刻を使用する。リレイヤー遅延で締切を越える可能性をUIで説明し、締切直前の受付保証を表示してはならない。

## 4. 音楽クリエーター初期登録時刻の正本

`R_c`は、ガバナンスが承認した音楽クリエーター登録台帳またはその監査済みアダプターから取得する。

- 再有効化、プロフィール更新、ウォレット変更、受取先変更または作品追加で`R_c`を更新しない。
- 登録解除後の再申請を同一音楽クリエーターとして復旧する場合も、審査済みの同一性対応付けにより元の`R_c`を維持する。
- 合併、分裂、改名または別活動名を同一音楽クリエーターとするかは権利・アイデンティティ審査で決定し、SBTコントラクトが推測しない。
- 登録時刻が存在しない、未確定、競合中または承認されていない登録台帳から返された場合は発行をfail closedとする。

本番では、テストネットの自己申告登録時刻を資格の正本にしない。Polygon Amoyで検証する場合も、その結果はテストネット資格に限定する。

## 5. ポリシー版とガバナンス

初期版を次のように提案する。

```text
policyId: CFP_EARLY_SUPPORTER_TIME_WINDOW
version: 1
windowSeconds: 31_536_000
lowerBoundInclusive: true
upperBoundExclusive: true
maximumEarlySupporters: none
effectiveFrom: ガバナンス実行マニフェストで確定
```

将来、コミュニティガバナンスは期間その他の条件をCFP、両院審議、仕様更新、監査およびタイムロックを経て変更できる。ただし、変更後のポリシーを過去の発行へ遡及適用せず、発行時に確定した階層とポリシー版を保存する。

本提案は現在のコントラクト構造を変更するため`P2`とする。監査済み実装が時間窓を安全な設定値として分離した後、その承認範囲内での将来の期間変更を`P1`とするかは別のガバナンス決定で定める。

## 6. 現行実装との差分

現在のテストネット用`SupporterSBTUpgradeable`は、音楽クリエーターごとに管理者が`earlyUntil`と`maxEarlySupporters`を設定し、次の条件で階層を選択する。

```solidity
policy.active
    && block.timestamp <= policy.earlyUntil
    && policy.earlyIssued < policy.maxEarlySupporters
```

この実装は本CFPに対して次の不一致を持つ。

1. 締切が初期登録時刻から自動導出されない。
2. 人数上限に達すると1年未満でも一般サポーターになる。
3. `<=`により締切時刻ちょうどを初期サポーターに含める。
4. SBT側の`bytes32 creatorId`と現行テスト登録台帳の`uint256 creatorId`を結ぶ承認済み対応付けがない。
5. 音楽クリエーター登録台帳の状態を発行時に検証しない。

したがって、現在のPolygon Amoyデプロイは本CFPへ適合していない。提案採択だけで既存コントラクトを適合済みと表示してはならない。

## 7. コードレベルの実装案

### 7.1 登録時刻インターフェース

SBTコントラクトは、特定実装のストレージ配置へ依存せず、ガバナンス承認済みの読み取り専用インターフェースを参照する。

```solidity
interface ICreatorInitialRegistration {
    function initialRegistration(bytes32 creatorScopeId)
        external
        view
        returns (uint64 registeredAt, bool current, uint64 registryVersion);
}
```

テストネットでは`CreatorFirstCreatorRegistry`の`uint256 creatorId`を正規の`bytes32 creatorScopeId`へ対応付ける明示的なアダプターを置く。本番では音楽クリエーター資格と権利登録を分離した承認済み登録台帳を使う。

### 7.2 判定関数

期間加算は`uint64`内で先に加算せず、`uint256`へ拡張して境界を比較する。

```solidity
function qualifiesForEarlyTier(
    bytes32 creatorScopeId,
    uint64 supporterRegisteredAt,
    uint64 windowSeconds
) public view returns (bool) {
    (uint64 creatorRegisteredAt, bool current,) =
        creatorRegistration.initialRegistration(creatorScopeId);

    if (!current || creatorRegisteredAt == 0) revert InvalidCreatorRegistration();
    if (supporterRegisteredAt < creatorRegisteredAt) revert InvalidRegistrationOrder();

    return uint256(supporterRegisteredAt)
        < uint256(creatorRegisteredAt) + uint256(windowSeconds);
}
```

発行処理は`supporterRegisteredAt = uint64(block.timestamp)`を一度確定し、判定結果、`creatorRegisteredAt`、`windowSeconds`、ポリシー版、登録台帳版を資格証明記録またはイベントへ結び付ける。人数上限を初期階層の条件に使用しない。

### 7.3 アップグレード

- 新実装をUUPS互換の別実装として作成し、ストレージレイアウト検査を通す。
- 登録台帳アドレスとポリシー参照を初期化用再初期化関数で一度設定し、個人管理者ではなくタイムロックへ権限を移す。
- 既発行トークンの`tier`と`policyVersion`を変更しない。
- 新しい判定を有効化するブロック番号とポリシー版を実行マニフェストへ固定する。
- 旧実装へのロールバックで新発行記録を解釈できなくなる場合は、ロールバックではなく一時停止と前方修復を使用する。

## 8. コードレベルの検証計画

### 8.1 単体テスト

Hardhatの時刻操作を用い、少なくとも次を検証する。

| テスト | 期待結果 |
| --- | --- |
| `registeredAt`と同じ時刻 | `EARLY_SUPPORTER` |
| `registeredAt + 31_535_999` | `EARLY_SUPPORTER` |
| `registeredAt + 31_536_000` | `SUPPORTER` |
| `registeredAt + 31_536_001` | `SUPPORTER` |
| `supporterRegisteredAt < registeredAt` | revert |
| 登録時刻がゼロ、未承認台帳、非現行音楽クリエーター | revert、SBT未発行 |
| 2人以上が期間内に登録 | 人数にかかわらず全員`EARLY_SUPPORTER` |
| 期間後の登録 | 人数にかかわらず`SUPPORTER` |
| 再有効化、プロフィール・ウォレット更新 | 初期登録時刻不変 |
| 同一音楽クリエーター・同一ユーザの再実行 | 二重発行拒否 |
| 発行後のポリシー変更 | 既発行階層とメタデータ不変 |

### 8.2 プロパティテスト

任意の`registeredAt`、`supporterRegisteredAt`および安全な`windowSeconds`について、次の性質を検証する。

```text
qualifies == (
  supporterRegisteredAt >= registeredAt
  && supporterRegisteredAt < registeredAt + windowSeconds
)
```

さらに、期間内の登録人数を増やしても各ユーザの判定が変化しないこと、順序を入れ替えても結果集合が変化しないこと、`uint64`上限付近でも加算がオーバーフローしないことをファズテストする。

### 8.3 統合テスト

1. 音楽クリエーター登録台帳へ音楽クリエーターを登録する。
2. 登録イベントと`registeredAt`をインデクサーで確定する。
3. 期間内と期間外でEIP-712支援意思を署名する。
4. リレイヤーからSBT発行を実行する。
5. オンチェーン階層、ポリシー版、登録台帳版、メタデータおよびインデクサー参照モデルが一致することを確認する。
6. リレイヤー受付は期間内でも、確定ブロックが締切以後なら一般サポーターになることを確認する。
7. チェーン再編、イベント重複、インデクサー遅延時に資格を早期有効化しないことを確認する。

### 8.4 ガバナンス実行検証

提案を実行可能にする段階では、次を一つの不変な実行マニフェストへ固定する。

- CFP IDと版
- 更新後の`SPEC-ACCOUNT-004`のハッシュ
- チェーンID、プロキシ、旧実装、新実装、コードハッシュ
- 登録台帳またはアダプターのアドレスとコードハッシュ
- `windowSeconds = 31_536_000`
- 上限境界が排他的であることを示すテスト成果物ハッシュ
- ストレージレイアウト差分、監査報告、ソースコミット
- UUPS `upgradeToAndCall`の正確なcalldata
- 有効化時刻、タイムロック、停止・前方修復手順

自然言語、仕様、テスト、ビルド成果物およびcalldataのいずれかが一致しない場合、投票開始または実行を停止する。

テストネット用ガバナーとCREATE2デプロイファクトリーを用い、次をローカルHardhat試験として実装した。

- [憲章適合性レビュー](./reviews/CFP-0002-charter-review.md)と[法務実行可能性レビュー](./reviews/CFP-0002-legal-review.md)の実ファイルハッシュを投票前証拠として登録する。
- [音楽クリエータ院議会の合成議事録](./records/CFP-0002/revision-0001/creator-house/minutes-001.md)と[ユーザ院議会の合成議事録](./records/CFP-0002/revision-0001/user-house/minutes-001.md)を院別に登録する。
- [CFP文書管理方式](./record-management.md)に従い、論点、議事録、院別議決および証拠索引を同じRevisionへ結合する。現在は未解決の重大論点とテストfixtureを含むため、本番投票・デプロイゲートには合格しない。
- 適合性審査が不合格、またはどちらか一院の熟議記録がない場合、議員の投票をコントラクトが拒否する。
- 両院が別々に定足数と賛成スコアを満たした後だけ、事後実装レビューとP2タイムロックへ進む。
- 両院承認後、[CFP-0002コントラクト試験証跡](./reviews/CFP-0002-contract-test-evidence.md)に従い、対象ソース、生成物、テストスイート、試験報告および承認済みcalldataのハッシュを登録する。
- テスト証跡がない、不合格、または別calldataに対する証跡である場合、実装レビューとデプロイを拒否する。
- タイムロック前、変更されたcalldata、議会を経ない直接呼出しではポリシーをデプロイできない。
- タイムロック後だけ、承認されたsalt・登録時刻アダプター・CFPハッシュ・仕様ハッシュから予測したアドレスへポリシーコードが作成される。
- デプロイ後のポリシーが`31,536,000秒`と排他的上限を保持することを境界値で確認する。

対象試験は`test/CreatorFirstCFP0002Governance.ts`である。これはローカルの合成議員と合成レビューによる技術的な状態遷移検証であり、CFPの採択、正式な憲章適合判定、弁護士の法律意見、実在議員の熟議、独立監査、Polygon Amoyまたはmainnetへのデプロイを意味しない。

## 9. 受入条件

- 音楽クリエーターの変更不能な初期登録時刻を承認済み正本から取得できる。
- 1年を`31,536,000 seconds`、上限を排他的として実装・UI・仕様が一致する。
- 人数上限が初期サポーター資格へ影響しない。
- 境界値、ファズ、再実行、再編、アップグレードおよびストレージレイアウト試験が成功する。
- 既発行SBTの階層と発行時ポリシー版が変更されない。
- 一般／初期サポーターSBTが譲渡不能であり、失効・Burn・ウォレット回復境界を維持する。
- 両院承認、株式会社の法務・セキュリティ確認、独立監査およびタイムロックを完了する。
- Polygon Amoyでの予行演習後も、テストネットデータ、鍵、SBTまたはコントラクトを本番へ移行しない。

## 10. 影響と留意事項

### 音楽クリエーター

全音楽クリエーターへ共通の初期期間を適用できる一方、活動開始日ではなくプラットフォーム初期登録日を基準とする。既に活動歴が長い音楽クリエーターでも、プラットフォーム登録後365日間は初期期間となる。

### ユーザ

条件を予測しやすくなるが、公開SBTによりウォレットと支援対象の関連が公開され得る。発行前の説明と明示的同意、Burn・失効・ウォレット回復手続が必要である。

### 法務・経済

資格を支払額、投資額、将来収益または換金可能性と結び付けない。限定特権を追加する場合は、消費者保護、景品、契約、税務、権利およびプライバシーを別途審査する。

## 11. 代替案

### 音楽クリエーターが任意の締切を設定する

柔軟だが、音楽クリエーター間で意味が不統一になり、締切変更の恣意性が生じるため初期版では採用しない。

### 先着人数上限を併用する

同じ期間内でも登録順序やリレイヤー混雑によって資格が変わるため採用しない。

### 支援意思の署名時刻を使う

クライアント時計や未確定署名を正本にできず、再実行・遅延・検閲への追加設計が必要なため初期版では採用しない。

### カレンダー上の翌年同月同日を使う

うるう年、月日および実装差が生じるため、初期版では固定`365日`を採用する。

## 12. 未決定事項

- テストネットの`uint256 creatorId`と正規`bytes32 creatorScopeId`を結ぶアダプター仕様
- 本番音楽クリエーター登録台帳の承認主体、状態および初期登録時刻の訂正手続
- リレイヤーが締切直前に受け付ける最小残時間とUI表示
- ポリシー期間の将来変更を`P1`として許す範囲
- 初期サポーターへ接続できる具体的なコミュニティ特権

これらは採択・実装前に、`OQ-EARLY-SUPPORTER-001`等の決定記録へ接続する。
