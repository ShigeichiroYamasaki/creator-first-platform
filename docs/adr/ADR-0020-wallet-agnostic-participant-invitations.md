# ADR-0020: ウォレット未確定型の事前登録と本人登録

**状態:** 提案

**日付:** 2026-08-28

**最終更新日:** 2026-09-03

## 背景

公開実験は事前登録制とする一方、運営が申込時点でユーザまたは音楽クリエーターのEOAを把握できるとは限らない。メールアドレスをオンチェーン識別子へ変換すると辞書攻撃、永続的な紐付け、訂正困難性が生じる。また、未登録者が最初のガス代を持たない状態でオンチェーン本人登録を必須にすると循環依存になる。

## 決定

参加申請、運営審査、連絡先とウォレットの同時確認、オンチェーン準備および役割登録を、監査上は分離しながら参加者には一つずつ提示する。承認された参加者の通常経路で送るメールは一通とする。

1. 募集期間中、申請者は体験ページから表示名、連絡用メール、ユーザ／音楽クリエーター役割および一つに束ねた必須確認を送る。ウォレットは収集しない。
2. 必須確認は、表示中の実験条件、利用条件および個人情報の取扱いの版を一つの同意束として記録する。宣伝メールその他の任意目的はこの必須確認へ混ぜない。
3. 申請は `SUBMITTED` として運営審査へ進める。この時点のメールは未確認であり、運営は表示名やメールを本人確認済み情報として扱わない。募集コード、率制限、重複表示および人による審査で不正・誤送信リスクを抑える。
4. 承認時、ゲートウェーは256 bitの一回限り招待トークンを生成し、データベースには一方向ダイジェストだけを保存する。承認、メール所有確認および参加登録を一つのリンクから開始できる参加メールを一通だけ送る。却下時は招待を作らず、却下通知を送る場合もその申請に対する一通として扱う。
5. 招待URIのトークンはURL fragmentへ格納し、HTTPリクエスト、アクセスログまたはRefererへ通常送信されない形にする。メールクライアントのリンク検査やプレビューだけでは確認済み・使用済みにせず、参加者による明示操作と署名成功まで消費しない。
6. 参加者は招待ページで申請時の表示名、役割、期限および要点を確認し、一つの必須チェックを行う。次に任意のMetaMask EOAを選び、招待ID、承認対象役割、同意束の版およびPolygon AmoyのチェーンIDを含むSIWE形式メッセージへ署名する。汎用ログイン署名だけでは招待を取得できない。
7. ゲートウェーはトークンと署名を同時に検証し、メール到達確認、同意、ウォレット所有確認および招待取得を一つの冪等なサーバ処理として確定する。メールアドレス、ウォレットおよび法的本人が同一人物であることまで証明したとは扱わない。
8. ウォレット署名と招待取得が確定すると、運営ワーカーは結び付け後のEOAだけをオンチェーン参加者登録台帳へ自動承認し、既存のテストPOL配布上限内で初回資金を供給する。参加者は追加のトランザクションを送らない。
9. 自動処理は参加者IDと操作IDで冪等化し、最終的な役割登録トランザクション、リレイヤー、テストPOL配布および失敗時再実行を、申請、審査、メール配信、招待取得と別の監査状態として扱う。失敗または中断した処理は運営ワーカーが定期照合して同じ識別子で自動再試行する。同じ運営EOAからのオンチェーン送信はNonce競合を避けるため直列化し、通常の管理画面には手動実行ボタンを置かない。

### 監査状態と参加者向け表示を分離する

監査状態は少なくとも `SUBMITTED`、`UNDER_REVIEW`、`INVITATION_DELIVERY_PENDING`、`INVITATION_SENT`、`INVITATION_CLAIMED`、`REJECTED`、配信失敗、オンチェーン承認、初回テストPOL配布および役割別登録を区別する。一方、参加者ビューは状態履歴をすべて同時表示せず、サーバが返す現在の表示状態から、次に必要な主操作を一つだけ示す。

| 現在の状態 | 参加者へ表示する内容 | 主操作 |
| --- | --- | --- |
| 未申請 | 表示名、メール、役割、必須確認 | `確認して申請する` |
| `SUBMITTED` / `UNDER_REVIEW` | 「運営が確認しています」 | なし |
| `INVITATION_SENT` | 「参加メールを確認してください」 | 通常はなし |
| 招待リンクを開いた未取得状態 | 申請内容、期限、一つの必須確認 | `仮想通貨ワレットを開く` |
| ウォレット確認済み・未取得 | 確認したウォレットの短縮表示 | `この内容で登録する` |
| `INVITATION_CLAIMED`・準備中 | 「運営が準備しています」 | なし。自動更新 |
| オンチェーン承認・POL配布完了 | 「実験参加登録完了」 | 役割別体験へ進む |
| 回復可能な失敗 | 原因を一般向けに説明 | その失敗専用の再試行一つ |

完了済みの入力フォーム、操作ボタンおよび詳細な工程は既定で隠す。参加者が確認を必要とする場合だけ「完了した手順を見る」で読み取り専用の要約を開けるようにする。未到達の将来工程は操作可能になるまで表示しない。進捗表示を置く場合も、全ボタンを並べず「現在の段階」と全体のおおよその位置だけを示す。

### 回復操作を必要時だけ提示する

メール再送は `INVITATION_SENT` のまま一定時間が経過し、招待が未取得・期限内で、サーバ側の再送可能時刻と上限を満たす場合だけ「メールが届かない場合」の中へ表示する。初期運用値は送信後5分、再送間隔10分、24時間内3回までとし、設定値と監査記録で変更可能にする。再送時は以前のトークンを無効化し、新しい一回限りトークンを発行する。クライアント側の表示制御だけに依存せず、ゲートウェーが時刻、回数、状態および冪等性を強制する。

同様に、接続再確認は接続失敗時、ウォレット案内は署名待ち時だけ表示する。参加者にも管理者にも、運営ワーカーが所有するオンチェーン処理の実行ボタンを出さない。管理画面は審査操作と読み取り専用の自動処理状態だけを表示し、失敗時は監査記録を残したまま定期照合で回復する。

ユーザと音楽クリエーターの両方で招待された場合、招待、同意およびウォレット所有確認は一度だけ行い、オンチェーン役割登録とサービス利用は役割ごとに分離する。

### APIの参加者向け状態投影

参加者向けAPIは内部状態名や管理操作をそのまま返さず、少なくとも次の表示契約を返す。

```text
participantView = {
  phase,                 // APPLY | REVIEW | CHECK_EMAIL | CONNECT_WALLET | REGISTER | PREPARING | READY | RECOVERY
  title,
  guidance,
  primaryAction,         // 0または1個
  actionOwner,           // PARTICIPANT | OPERATOR | NONE
  completedSummary,
  recoveryAction,        // 条件成立時だけ存在
  recoveryAvailableAt,
  refreshAfterSeconds
}
```

クライアントは内部状態を推測してボタンを組み立てず、この投影に従う。ただし、危険な操作の認可、再送可否、回数制限およびオンチェーン状態の確定は常にサーバまたは対象コントラクトが再検証する。表示契約の文言は日本語・英語で対応付け、支払い、権利、本人確認または本番資格を誤認させない。

### 旧フローからの移行

既存データを一括して新状態へ書き換えず、データベースのスキーマ版と申請フロー版を追加する。旧フローで発行済みの確認リンクと招待は、その有効期限まで旧処理で完了できるようにし、新規申請だけを `PARTICIPANT_ENROLLMENT_V2` へ切り替える。移行期間中、APIは各申請のフロー版に従い、旧確認トークンを新しい統合招待として解釈しない。

V2の通常経路は次の順序とする。

```text
申請
  → 運営審査
  → 承認・統合参加メール一通
  → 明示確認・ウォレット署名・招待取得
  → 運営ワーカーによるオンチェーン承認と初回POL配布の自動処理
  → 役割別の実験利用開始
```

切替前に、既存Cookieセッション、旧確認メール、旧招待、二重送信、メール配信失敗、リンク検査、期限切れ、再送競合、ウォレット変更、オンチェーン失敗および二重クリックを含む移行試験を行う。

管理画面は公開デモのナビゲーションへ掲載せず、`noindex`とする。運営にはGitHub Pages上の固定URLを提供し、そこから公開ランタイム情報で現在のGoogle クラウドVM上の管理画面へ遷移させる。ただしURL秘匿を認証とはみなさず、全管理APIに高エントロピーBearer tokenを要求する。管理トークンとメール送信APIキーはゲートウェーの秘密ファイルだけに置き、静的JavaScript、URLまたはブラウザ保存領域へ埋め込まない。

ローカル試験のメールはOutboxへ保存する。本番相当試験では、ゲートウェーから認証付きWebhookを通じてメール事業者へ送信する。メール送信結果は配信受付であり、メール所有確認、ウォレット確認または本人登録成功を意味しない。

初期の少人数実験に限り、`11rou.yamasaki@gmail.com`を送信元とするTLS接続のGmail SMTPを使用できる。Googleアカウントの通常パスワードは使用せず、2段階認証下でゲートウェー専用に発行したアプリパスワードを実行環境の秘密情報として保持する。アプリパスワードをGit、静的サイト、ログ、監査イベント、VMの恒久メタデータまたは参加者向け応答へ含めない。送信は承認後の参加メール、却下通知、必要になった再送および重要な運用通知に限定し、送信量制限、迷惑メール判定、資格情報失効および個人アカウント依存を監視する。これは本番メール基盤の決定ではなく、本番移行前に独自ドメインのトランザクションメール、送信ドメイン認証、苦情・バウンス処理および役割分離を再決定する。

GitHub Pagesは静的な案内だけを提供し、参加申請を自身の`/api`へ送らない。実際の参加申請、Cookieセッション、メール到達確認および招待取得は、Google クラウドVM上で画面とAPIを同じHTTPSオリジンにしたクラウド版で行う。参加メールは、サーバ再起動で失効しない固定入口を使用する。無償実験ではVMの静的外部IPv6、`nip.io`の固定ホスト名およびCaddyの自動TLSを組み合わせ、GitHub Pagesの固定入口はURL fragmentを保持したまま、検証済み公開ランタイム情報からこのクラウド版へ遷移する。これによりCORS許可や第三者Cookieを参加条件にしない。固定ホスト名の稼働確認と公開ランタイム情報の一致を公開再開条件とし、一般参加の本格化前には運営主体が管理する独自ドメインへ移行する。

> **実装ノート（2026-09-03）:** Polygon Amoyの参加者登録台帳、運営ワーカーによるオンチェーン承認と初回テストPOL配布、役割別の本人登録に加え、V2の一メール化、単一必須確認、状態駆動表示、条件付き再送、再送時のトークン更新、GitHub Pages固定入口でのfragment保持、招待取得後の冪等な運営ワーカー自動起動、および失敗・再起動後の定期自動照合を実装した。管理画面の招待状況は読み取り専用とし、オンチェーン運営処理の手動実行を通常経路から削除した。共用端末では、既存申請を削除せずブラウザセッションだけを明示的に切り替え、別の実験参加者が連続して申請できる。既存V1申請の確認リンクと二確認項目は有効期限内の互換経路として残す。Google クラウドVMでは静的外部IPv6、`nip.io`固定ホスト名およびCaddyの自動TLSを採用した。本番用管理認証、運営主体が管理する独自ドメイン、本番アカウント登録および実参加者による一連試験は未成立である。

## プライバシー・セキュリティ境界

- メール、氏名、招待トークンまたはその単純ハッシュを公開チェーンへ記録しない。
- 招待の閲覧APIはメールアドレスを返さない。
- 申請状態APIはメールアドレス全体を返さず、本人向けのマスク済み表示だけを返す。未認証の照会結果からメールの登録有無を推測させない。
- ウォレット署名はウォレット操作能力だけを示し、法的本人確認、音楽クリエーター資格、権利保有または受取人確認を意味しない。
- 音楽クリエーター資格は招待役割とは別に、権利・本人・受取人審査を必要とする。
- 管理画面をGitHub Pagesから利用する場合も、管理APIは専用HTTPSオリジンまたは同一オリジンのリバースプロキシで提供する。
- 本番ではBearer token単独から、パスキー、短命管理セッション、役割分離、監査、レート制限へ移行する。

## 影響

参加希望者は通常一通のメールと一つずつ提示される操作で参加でき、運営はEOAを事前収集せず審査・承認できる。完了済みや未到達の操作を隠すため、誤操作、不要な再送および無効ボタンへの混乱を減らせる。参加者は承認後の本人登録時に利用するウォレットを自ら選択する。

一方、未確認メールを含む申請を運営が審査するため、募集コード、率制限、重複検知および配信失敗処理が必要になる。画面表示用状態と監査状態を分けるAPI契約、旧フローとの版管理、固定HTTPS入口、メール等の個人情報を扱うゲートウェー、およびオンチェーン登録・ガス補助を連携する運用ジョブも必要になる。静的GitHub Pagesだけでは申請受付、メール送信または安全な管理者認証は完結しない。

## 採用しなかった代替案

- **EOAを申込フォームで事前収集:** 初心者負担が高く、入力誤りとウォレット変更に弱い。
- **メールアドレスのハッシュをオンチェーン登録:** 低エントロピー識別子で再識別されやすい。
- **招待コードだけで即時登録:** 転送・窃取した者による取得を防ぎにくい。
- **ブラウザへメールAPIキーを埋め込む:** キー流出と第三者送信を防げない。
- **申請直後の確認メールと承認後の招待メールを維持:** メール所有確認を審査前に完了できるが、参加者に二つのリンクと待機状態を理解させる認知負荷が大きいため、V2の通常経路には採用しない。
- **全工程と全ボタンを一画面へ常時表示:** 状態は見えるが、完了操作の再実行、不要な再送および無効ボタンへの混乱を招くため採用しない。

## 受入基準

1. 承認された新規V2申請の通常経路で、申請から役割登録開始までに送られる参加メールが一通である。
2. 申請時および招待取得時の参加者向け必須チェックが、それぞれ一つを超えず、任意目的の同意を含まない。
3. 各参加者画面で主操作が同時に二つ以上表示されず、完了済みフォームと未到達操作が既定で表示されない。
4. メール再送はサーバが返す再送可能状態と時刻になった場合だけ表示され、直接APIを呼んでも状態、期限、間隔および上限が強制される。
5. 招待URLの取得またはメールクライアントによるリンク検査だけでは、メール確認、招待取得またはトークン消費が発生しない。
6. SIWE署名が招待ID、役割、同意束の版、ウォレットおよびPolygon Amoyへ結び付き、別招待・別役割・別チェーンで再利用できない。
7. メール配信、招待取得、オンチェーン承認、POL配布および役割登録が別の監査イベントとして復元できる。
8. 参加者に責任のないオンチェーン処理失敗では、参加者画面に運営用再実行ボタンが表示されない。
9. 固定入口が許可済みの稼働中オリジンだけへURL fragmentを保持して遷移し、異常時はトークンを送らず停止する。
10. 旧フローの有効な申請・確認リンク・招待が移行期限まで処理でき、新旧トークンを相互に取り違えない。
