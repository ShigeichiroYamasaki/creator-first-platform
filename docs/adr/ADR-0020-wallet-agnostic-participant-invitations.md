# ADR-0020: ウォレット未確定型の事前登録と本人登録

**状態:** 提案

**日付:** 2026-08-28

**最終更新日:** 2026-08-29

## 背景

公開実験は事前登録制とする一方、運営が申込時点でユーザまたは音楽クリエーターのEOAを把握できるとは限らない。メールアドレスをオンチェーン識別子へ変換すると辞書攻撃、永続的な紐付け、訂正困難性が生じる。また、未登録者が最初のガス代を持たない状態でオンチェーン本人登録を必須にすると循環依存になる。

## 決定

事前登録、本人によるウォレット選択、オンチェーン資格登録を分離する。

1. 管理者はゲートウェーの管理者APIで参加者名、連絡用メール、ユーザ／音楽クリエーター役割、有効期限を登録する。
2. ゲートウェーは256 bitの一回限りトークンを生成し、データベースにはSHA-256ダイジェストだけを保存する。
3. 招待URIのトークンはURL fragmentへ格納し、HTTPリクエスト、アクセスログまたはRefererへ通常送信されない形にする。
4. 参加者は招待ページで任意のMetaMask EOAを選び、Polygon Amoyを指定したSIWE形式メッセージへ署名する。
5. ゲートウェーは署名を復元検証し、招待をそのEOAへ一回だけ結び付ける。
6. 運営処理は結び付け後のEOAだけをオンチェーン参加者登録台帳へ承認し、既存のテストPOL配布上限内で初回資金を供給する。
7. 最終的な役割登録トランザクション、リレイヤー、テストPOL配布および失敗時再実行は、オフチェーン招待の成功と別の監査状態として扱う。

参加者ビューは、管理者の事前登録、メール送信、招待確認、ウォレット所有確認、招待取得、オンチェーン承認、初回テストPOL配布および役割別本人登録を一つの成功状態へまとめない。現在完了した段階、次の操作、その操作の担当が参加者または運営のどちらかを表示する。ユーザと音楽クリエーターの両方で招待された場合、招待とウォレット所有確認は一度だけ行い、オンチェーン役割登録とサービス利用は役割ごとに分離する。

管理画面は公開デモのナビゲーションへ掲載せず、`noindex`とする。ただしURL秘匿を認証とはみなさず、全管理APIに高エントロピーBearer tokenを要求する。管理トークンとメール送信APIキーはゲートウェー環境変数だけに置き、静的JavaScriptへ埋め込まない。

ローカル試験のメールはOutboxへ保存する。本番相当試験では、ゲートウェーから認証付きWebhookを通じてメール事業者へ送信する。メール送信結果は配信受付であり、本人登録成功を意味しない。

## プライバシー・セキュリティ境界

- メール、氏名、招待トークンまたはその単純ハッシュを公開チェーンへ記録しない。
- 招待の閲覧APIはメールアドレスを返さない。
- ウォレット署名はウォレット操作能力だけを示し、法的本人確認、音楽クリエーター資格、権利保有または受取人確認を意味しない。
- 音楽クリエーター資格は招待役割とは別に、権利・本人・受取人審査を必要とする。
- 管理画面をGitHub Pagesから利用する場合も、管理APIは専用HTTPSオリジンまたは同一オリジンのリバースプロキシで提供する。
- 本番ではBearer token単独から、パスキー、短命管理セッション、役割分離、監査、レート制限へ移行する。

## 影響

運営はEOAを事前収集せず参加者を承認でき、参加者は登録時に利用するウォレットを自ら選択できる。一方、メール等の個人情報を扱うゲートウェーと、オンチェーン登録・ガス補助を連携する運用ジョブが必要になる。静的GitHub Pagesだけではメール送信も安全な管理者認証も完結しない。

## 採用しなかった代替案

- **EOAを申込フォームで事前収集:** 初心者負担が高く、入力誤りとウォレット変更に弱い。
- **メールアドレスのハッシュをオンチェーン登録:** 低エントロピー識別子で再識別されやすい。
- **招待コードだけで即時登録:** 転送・窃取した者による取得を防ぎにくい。
- **ブラウザへメールAPIキーを埋め込む:** キー流出と第三者送信を防げない。
